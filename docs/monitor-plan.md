# 低频余位监测设计（v0.3.3）

v0.3.0 已实现下述单活动监测、界面和离线测试。本轮开发没有连接学校或执行真实预约；人数协议依据来自此前只读检查，见 [当前人数证据](capacity-evidence.md)。长期后台运行与真实捡漏效果仍待实际使用验证。

## 已有接口依据

此前实测及现有接口层支持 `POST /gsapp/sys/yddjzxxtjappseu/modules/hdyy/queryActivityList.do`，空表单、学校同源登录态。一次响应包含：

- `hdlbList`：活动 `WID`、`HDZRS`（容量）、预约起止时间、取消状态。
- `hdrsList`：按 `HD_WID` 关联活动，`YYRS` 是已预约人数。
- `xsxxList`：按 `WID` 关联个人预约，`YY_WID` 非空表示已有预约。

人数均完整有效时，估计余位为 `max(0, HDZRS - YYRS)`。这不是占位凭证；名额最终由提交接口决定。没有验证更小的专门余位接口、推送接口或服务端人数更新／缓存延迟，不猜新接口。

`Api.list()` 保留 `countKnown`，区分“未知”与“确实为零”。缺失人数行可以出现在学校正常响应中（学校前端默认显示零）；本版监测保守等待完整人数，不据此触发自动预约。缺失、非法或不一致数据不触发自动预约。一次请求即可服务所有已选活动，不能为每个活动分别轮询整份列表。

## 第一版范围

支持一个明确选中的活动。页面新增按钮统一为“预约助手”，同一弹窗提供“定时预约／余位监测”和 OCR／手动选择。满员默认监测并禁用定时预约，其余默认定时；打开弹窗仅获取信息和预热 OCR，由用户点击主要按钮启动任务。定时任务可勾选“未抢到时继续监测余位”。活动已取消／结束或本人已预约则不提供启动。

v0.3.1 监测面板保留活动标题、人数／容量、倒计时和操作控件；状态体仍记录上次检查时间，但常态不单独显示说明文字。支持收起，卡片显示“监测中”，点击恢复同一弹窗；验证码或结果需处理时自动展开。模式由用户主动开启，不因打开学校页面而启动；不保存凭据，不自动登录。

默认每 60 秒检查一次，可选 30／60／120 秒，加入约 ±10% 随机偏移。此为请求预算选择，未获知学校限额。第一次立即查询，后续在上一次请求完成后安排下一次，不并发、不因计时延迟补发历史请求。

v0.3.3 修改间隔只更新设置，不重排当前等待；当前查询完成后再采用最新间隔。“立即检查”位于“停止监测”左侧，取消原倒计时并复用同一个列表查询入口，完成后按当前设置重新计时，不加额外冷却。请求期间按钮禁用，自动／手动共用单请求互斥，避免重复循环。尚未开放或网络故障退避期间不能用它跳过等待；暂停时使用“继续监测”，验证码及提交阶段隐藏立即检查。

监测进入时启用 OCR 并禁用手动选项；识别失败／不完整或验证码被明确拒绝时，间隔 1 秒自动换图，每轮最多处理 3 张。模型资源不可用或耗尽尝试后回退手动并开放选项；用户主动重新选择自动才开始新的预算。定时预约的模式偏好独立保存，监测不会将其覆盖；切回定时预约恢复先前选择。

## 状态与提交

```text
启动 → 预热 OCR → 低频查询列表
                  ├ 未开放 → 等到开放时间（期间不轮询）
                  ├ 余位为 0／人数未知 → 等待下一轮
                  ├ 已有个人预约 → 成功结束
                  ├ 活动取消／预约结束 → 结束
                  └ 有余位 → 暂停轮询 → 取验证码 → OCR／手动 → 提交 → 核验
```

发现余位后直接复用刚取得的活动数据和时间偏移，不为了检查按钮再刷新页面或重复获取整份列表。不调用资格检查接口，不提前或定时刷新验证码。取图前后都不能假定名额已经锁住。

业务失败提示明确包含“人数已满”时切换为监测模式：原本正在监测或定时任务事先勾选了后续监测，则按低频间隔继续查询；其他情况回到待启动状态，提供可点击的“开始监测”，不自动启动。用户截图已显示真实界面提示“当前活动预约人数已满，请重新选择”，但服务端原始响应的完整外壳尚未采集；测试用这一提示配合模拟响应验证恢复分支，不将模拟外壳标为实测。其他未知业务提示显示原文并停止。

满员失败后将原人数快照标为待确认，并保留明确满员标志，禁用直接预约；直到新的列表响应更新人数。清除旧验证码、计时任务及未完成识别的结果，防止切换 OCR 后再次提交旧图。验证码错误和 OCR 识别失败按有限预算自动换图重试，耗尽后交回手动；提交网络结果不明先核验，不自动再次提交。成功后终止监测、同步助手按钮。

v0.3.2 将界面控件与请求入口的可操作条件集中管理：提交前可切换预约方式，取消旧任务并回到待启动状态；定时预约还要求当前未满员。提交、核验、结果待确认以及终态锁定模式。OCR／手动只影响当前有效验证码；迟到的取图和识别结果不能恢复已经切换掉的任务。请求入口也检查满员、取消、结束和已有预约，不能只依赖禁用按钮。

## 长时间运行

- 网络故障按 2、4、8、8 分钟退避，连续第 5 次仍失败则暂停；成功响应后恢复默认周期。登录／权限错误暂停；429 停止或遵从明确 Retry-After。
- 整个监测及预约流程共用现有跨标签页锁。取验证码、输入、提交、核验期间无第二个监测循环。
- 必须保留浏览器页面和有效登录态。后台页面节流、电脑休眠会延迟检查，不能承诺固定周期的后台常驻服务；唤醒时只补一次当前查询。
- “关闭／停止监测”或导航离开结束未提交任务；“收起”继续运行。刷新后不恢复监测配置和任务，每个新任务默认 60 秒，用户主动选择和启动；仅 OCR／手动偏好持久化。

## 离线验收（已实现测试）

模拟满员→余位释放、持续有余位、两次检查之间余位被占、字段缺失、活动结束／取消、已有预约、网络退避、登录失效、限流、休眠延迟、暂停／停止、跨标签页互斥和结果不明。断言每轮只有一次列表请求，满员不取图，预约期间停止轮询，成功后不再请求或提交。

## v0.2.1 状态修复

v0.2.0 成功阶段只通知 Dialog，Mount 的按钮文字写死为“定时预约”。v0.2.1 在核验成功后将 `activity.reserved` 置真并通知 Mount，新增按钮变为“已预约”；仍可点击重新查询，便于处理随后在学校页面手动取消的情况。初始列表的预约状态也用于按钮，迟到的旧列表不覆盖后来的核验结果。

不直接把学校原按钮改成“取消预约”，否则其原 Vue 点击处理可能仍是预约动作。成功弹窗新增用户主动点击的“刷新学校页面”，由学校自己的加载流程恢复原按钮和人数。仅修饰原按钮文字不能替代实际状态同步。
