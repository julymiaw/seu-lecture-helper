# 当前设计

0.7.1 固定提前 30 秒取图，已移除时间选择项和 configure；旧恢复记录中的提前量不参与当前调度。倒计时水平居中。日志实现与导出格式见 docs/diagnostics.md，下文旧版本段落保留设计演进。

单任务状态机：打开查询 → 显式启动 → 开放前 30 秒后台取图并识别 → 开放时提交 → 核验记录。验证码图片与数字不进入界面。

开放计时与异步取图／识别独立，等待期间每分钟取验证码检查会话，不识别；距最终取图不足 20 秒时不再启动检查，已有检查结束后才取最终图片，避免并发刷新验证码。默认提前 30 秒；不早于开放时间提交。换图清空旧答案，只保留同一轮图片对应的 OCR 答案；generation 与 ocrEpoch 拒绝迟到结果。提交与核验期间不能关闭。

识别失败、不完整数字、明确验证码拒绝或“尚未开放预约”直接换图再试，开放前识别失败同样立即换图；只有四位数字且已开放才自动提交，不查询人数；收到满员、结束、限流提示时停止；HTTP 登录失效时暂停并保留任务。“已预约”转入核验。没有长期余位监测。网络写入结果不明先核验，避免重复写入。

验证码图片和答案只保存在当前任务内存中。OCR 资源与诊断日志分别缓存；日志只记录选定的安全字段。真实验证码有效期未验证，提前时间固定为 30 秒。

待执行任务只在同一标签页的 sessionStorage 保存目标、提前时间、截止时间与核验标志。刷新或正常登录返回后重新查询目标，重新取图；已进入提交／核验的任务不查活动元数据，直接恢复核验，预约截止后仍保留待核验屏障。完成、明确失败、显式关闭清除记录；pagehide 清理运行对象但保留意图。统一认证硬过期和电脑休眠不能靠会话检查保证解决。

## 0.6.0：同一讲座的两个候选

只扩展现有 Reservation，不引入通用多任务框架：State 保存最多两个候选、当前索引与优先模式。标题前两组括号分别解析模式、类别；以类别、剩余名称、讲座起止时间配对，只有唯一匹配才提议加入。用户确认后启用候选组，拒绝则 single(id) 保留点击目标。未知模式阻止启动，允许在面板内选择场次并应用标注。两个挂载按钮复用同一面板。优先顺序仅 ready 阶段可改。

advanceCandidate 仅由 addReservation 的 business/full 分支调用；等待当前响应完成才切换索引，清空旧图及答案、使旧异步回调过期，再按新目标的开放时间取新图。无额外固定等待或人数查询；验证码错误、未开放不改索引。超时／格式错误转核验，登录和限流不转候选。整体 Web Lock 不变，只有一个执行器和验证码会话检查。

双候选容量以业务满员响应决定；单目标仍保留页面查询的满员拦截。任一候选已有关联预约记录时不启动另一份预约。完成后不自动取消。

sessionStorage 的 v2 记录保存两个 ID、索引、顺序与手动标注；提交阶段先保存 verify 屏障。恢复时固定目标和候选顺序，不重新自动匹配。旧记录没有候选数组时仍恢复为单目标，不能静默升级。验证码和答案不持久化。

0.6.1 在主面板中增加 choosing 阶段，确认卡只展示另一场次名称和“是否加入？”，按钮为“取消／加入”，集中在右侧。确认前 start 不可用；应用场次标注也在该面板完成，不调用 window.confirm 或 window.prompt。

0.6.3 用 fullIds 记录明确满员的场次，恢复旧记录时只从已越过的候选索引还原满员项；初次打开时另一场次已有预约不因此把未尝试项标成已满。候选行随 phase 更新为等待／预约／核验／成功，成功页不再显示旧错误、提交和换图。末项明确满员时使用整体失败提示；服务端原文与处理决定仍写入 Console。配对确认只增加一句“是否将同一讲座的另一场次也加入候选？”。

## 0.7.0：仅 OCR 自动预约

移除验证码编辑、手动提交、手动换图与人工回退。prepared 阶段仅展示图片及只读数字，由倒计时或识别完成回调触发私有 submit；loadCaptcha 也只由状态机调用。OCR 准备共用一个进行中的 Promise，预热失败后使用时自动再试，若实际使用正在等待首次预热，预热失败后仍再尝试一次初始化；持续失败则终止并记录原因。识别错误仍立即串行换图，不设固定次数。

恢复登录再次失败时还原完整候选快照，避免 v2 记录退化成单目标。verify 记录不按预约截止时间删除，恢复时仅查询原 ID 的预约记录；无活动元数据的成功状态同样清除持久记录，元数据查询失败则保留旧意图。同页登录恢复直接核验，保留原活动及候选展示；冷恢复使用 verifiedId 更新对应“已预约”按钮。取图、初始化或识别完成时重新检查截止状态，避免停留在不可提交的 prepared。
