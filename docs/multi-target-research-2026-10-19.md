# 多目标与验证码调研（2026-10-19）

本轮只读取公开源码、现有本地代码和历史采集证据。没有访问学校接口、获取验证码、提交／取消预约或部署修改。当前本地版本 0.5.0，提交 3761c84。用户已明确本周艺术讲座采用**线上优先，满员转线下**；没有授权启动预约。

补充实施：随后用户将范围收敛为同一天只处理同一讲座的线上／线下两个版本，并要求只增加优先顺序控制项。0.6.0 因此直接扩展现有单执行器，不引入下文探索阶段的通用多任务协调器；实际行为与限制以 README 和 docs/design.md 为准。

## 结论

多目标排程与多请求并发不是一回事。已核对的实现中，有独立定时作业、有可重复点击注册的回调，也有排序后逐个预约；没有找到能证明“同一登录态同时准备两张有效验证码，且线上线下最多成功一个”的可靠实现或服务端契约。

建议先支持多个任务的排程，将同一讲座的线上／线下设为二选一候选组；保留同源锁，由一个协调器串行管理取图、识别、提交和必要核验。明确满员才切下一场次；提交不明先核验，不把超时当失败。用户当前选择没有授权“低优先场次抢先成功”或自动取消已有预约。

## 验证码：已知与未知

**已验证（历史实网样本，不是今天重测）：**

- 当前入口的 vcode.do 不带活动 ID，响应 datas 为完整 data URI；addReservation.do 才带 wid、vcode。
- 2026-10-14，同一未开放活动，同一张验证码，没有中途取图，第一次返回“尚未开放预约”，紧接着第二次返回验证码错误。两次请求总计约 81 ms。支持每轮提交后按需换新图，不依赖同码重复使用。原始记录位于项目外 evidence-2026-10-14/same-captcha-same-unopened-activity.json。
- 对未开放活动提交明确错误验证码也得到验证码错误，支持该路径中验证码拒绝可先于未开放提示，但不能还原后台全部判断顺序。

**根据源码推断：**

- 客户端没有传独立 challengeId；图像请求也不指定目标，因此不能给每个活动虚构一个独立验证码槽。服务端可能通过会话或账户关联验证码；具体键未知。
- 多个标签页一般仍共享同源登录会话，新增标签页不能当作验证码隔离。创建独立浏览器上下文也不能证明账户层验证码独立，本轮不建议这样规避协调。
- 学校错误消息提示“不要同时使用多台设备”，是并发干扰的警示，不是服务端绑定范围的源码证明。

**尚待实测／未知：**

- 取第二张是否立即覆盖第一张、是否允许多挑战并存、绑定会话还是账户、跨活动使用、并发原子性。
- 精确有效期。556973 介绍建议提前 30 秒至一分钟，493411 建议一两分钟；两者只是作者使用建议，没有服务端 TTL 或控制实验，不能据此写成确定 30／60／120 秒有效。
- 一个错误提交是否总消耗挑战，以及每一种业务拒绝的消费行为。一次同码失败不能证明所有状态都一样。
- 同时提交两个重叠活动，服务器是否原子互斥。现有 appiontCheck 前端调用不能证明 addReservation 在并发下互斥。

## 当前架构冲突与最小设计

现有 main.ts 单 current、lock.ts 同源单写锁、task-store.ts 单条恢复记录，reservation.ts 的取图互斥与每分钟验证码会话检查都按单任务设计。不能简单 new 两个 Reservation 并去掉锁：一个任务的会话检查就可能覆盖另一个最终验证码，且刷新恢复会互相覆盖。

最小修改方向：

1. 一个 Coordinator 持有现有同源 Web Lock，管理多个预约任务。每个任务是一个按用户优先级排序的候选组；不同日期的实际讲座分别排程。
2. 全局只允许一条“取图→OCR／人工修正→提交→必要核验”链；OCR 模型实例和下载缓存共享。会话检查也由协调器统一，最终验证码在用时不再另取保活图。
3. 本周艺术组顺序线上→线下；明确满员才取新图尝试线下。验证码拒绝在当前候选立即换图重试，不查人数；未开放也换图。网络超时、不可解析响应先核验当前候选，不因超时切线下。限流停止，登录失效保留整个队列。
4. 业务成功立即停止这个候选组的后续发送，再核验准确 WID 的有效预约。不会因核验短暂查不到就启动另一场次；结果不明时保留核验入口。其他日期、无冲突的任务不因这一组成功而删除。
5. 恢复存储改为带版本的任务列表、候选顺序、当前候选及是否存在未确认提交；不保存验证码或凭据。提交前持久化“需要核验”，刷新恢复先核验这个目标。旧单任务记录需要迁移。
6. 界面保持一个面板：候选顺序、倒计时、当前图片和可编辑答案、启动／停止。不同讲座可以加入待执行列表；避免每张卡片各自弹出独立执行器。

这个方案是同时排程、按优先级顺序备选；不承诺两份预约并发发送。严格优先级、最早一个成功即可、两个都保留是三种不同需求，不能混为一谈。用户本轮已选择第一种的“线上满员转线下”。验证码反复失败是否允许放弃线上转线下，尚未授权，因此不自行增加此条件。

## 为什么成功后取消另一分支不够

学校规则由今天事务对话只读核验：“禁止同一时间段预约并参加多场讲座。预约并参加多场讲座只计算一场有效讲座，其余讲座作违约处理。”本轮没有独立重读学校页面；这是转交的已读证据，不是公开源码能证明的服务端实现。

若两份写入都已到服务器，客户端看到先成功再 AbortController.abort() 不能撤回另一份服务器写入。事后取消需要额外用户授权，而且不能当作无风险互斥。因此没有服务端原子规则证据时，不将同时发送线上／线下作为默认实现。

## 离线测试计划与实网证据缺口

离线可测：多个同刻任务确定性排序、全局取图与提交无重叠、满员切候选并换图、验证码拒绝留在原候选、成功阻止后续发送、未知结果只核验、核验登录失败恢复、会话检查不覆盖最终图、刷新迁移与队列恢复、跨标签页只有一个协调器、任意任务终态不删除其他任务。

离线不能证明验证码寿命、覆盖和服务端原子互斥。若用户后续授权且工具规则允许，实网测试需单独设计：只读静态资源优先；验证码有效期／覆盖用控制变量分别记录取图、换图与提交时间，不能拿正常开放活动随意验证，不用“测试请勿预约”活动。没有足够证据前不为并发拆锁。
